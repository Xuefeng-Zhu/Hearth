# Hearth design review

Run 41 · November 26, 2026 · Reviewed `main` at `1f0b7da`

The most urgent design risk is the private Sprite boundary. Hearth delegates workspace authentication to that boundary, and deployment checks application health without checking URL access. The biggest reliability risks are job recovery after storage failures and the amount of work repeated by chat polling. This review confirmed no P0 security bug under the documented deployment model. The live Sprite access setting was outside the verification scope. This commit changes only this report.

## Architecture

- **HTTP and browser.** `hearth/server.py` wires the application and serves a static ES-module client through a threaded standard-library HTTP server. `web/app.js` coordinates navigation, chat, polling, and settings. Feature modules render Home, Memory, Artifacts, Timeline, Inbox and automation, Skills, and voice. Chat uses streamed POST responses. Timeline uses a separate SSE connection that signals filesystem changes.
- **Agent and routing.** `Application.enqueue` validates the thread and attachments and starts or adds to an in-memory FIFO. One loop processes each thread's turns serially. Different threads can run concurrently. `Agent.chat` persists the user message, loads the recent dialogue and optional rolling and cross-chat summaries, resolves skill and file intent, and retrieves memory and attachment context. `router.py` orders the model candidates by mode, intent, and recent model performance. `connectors.py` and `model_protocols.py` normalize gateway model calls, streaming, and tool exchanges. Mock supports an offline demo. Page creation has its own planner and generator.
- **Tools and side effects.** The parent turn filters advertised tools and executes them through the agent. `approvals.py` classifies effects and persists proposals and execution receipts. Typed adapters handle search, Browserbase, AgentMail, Box, Pinecone, and voice. One turn can delegate a batch to `workers.Pool`. Workers get their own conversation and a subset of tools, share the workspace approval policy, and return results for parent synthesis. Interactive workers may wait for approval. Scheduled workers can hand approval off to Inbox. The parent cleans the final text, writes the assistant message, links artifacts, and emits `done`. Memory tools can write during the turn. Optional summary and index work is queued off the reply path.

```text
Browser POST /api/chat
  -> HTTP validation / per-thread queue
  -> persist user turn -> recall, thread context, skills, attachments
  -> router -> model through Fly gateway (or Mock)
      ^                 |
      |                 v
      +------ tool results <- tool dispatch -> local services / connectors
                                              -> approval for gated effects
                                              -> optional workers -> evidence
  -> clean reply -> persist reply and link files -> SSE done -> browser
                        |
                        +-> rolling summary / memory index refresh
```

### Storage and background work

| Location | Contents and behavior |
| --- | --- |
| `HEARTH_DATA_DIR` (local default `.hearth/`) | `state.lock` coordinates file writes across threads and processes. Most durable writes replace one file atomically. Local checkpoints snapshot `live/`. Approval receipts, routing statistics, permanent forget rules and recovery journal, and scheduler secrets live at the data-root level. |
| `live/state.json` | Actions and approvals, reminder jobs and occurrences, recurring tasks and run history, Inbox and outbox, worker snapshots, Timeline activity, and metadata for skills, panels, files, and Pages. |
| `live/threads/`, `live/memory/`, `live/skills/` | Thread index and JSONL transcripts, per-thread summaries and raw attachments, seeded and edited Markdown memory, and user skills with revision history. Built-in skills ship with the code. |
| `live/artifacts/`, `live/pages/`, `live/browse/`, `live/index/` | Versioned generated files and HTML, browser screenshots, and derived recall data. Box can hold artifact copies. Pinecone is an optional derived remote index. An approved public Page is a versioned snapshot on the separate share service. |
| Sprite release and config | The installer switches a `current` symlink to a content-addressed release. Persistent data and configuration sit outside the release. Connector defaults and catalog ship with the app. Deployment and connector settings select connection IDs, with provider credentials supplied by the gateway. Native Sprite checkpoints can roll back the wider filesystem. Provider-side effects have their own lifecycle. |

The web process runs a two-second reminder loop that also triggers mail delivery, Inbox polls, Home and proactivity refreshes, and recurring tasks. The standalone scheduler process materializes due reminder occurrences as well. Email delivery uses a dedicated cross-process lock and retry state. Signed reminder actions update the occurrence under the state lock. An optional externally triggered tick wakes the Sprite and runs catch-up work. Other background work includes rolling summaries, local reindex and Pinecone sync, checkpoint restore, the Timeline watcher, and session cleanup. Queued chat turns and summary requests live in memory. Reminder occurrences and task run claims are durable.

## API boundary and validation

Paths below are relative to `/api`. Each workspace route relies on the same single-workspace Sprite identity boundary in production. Local development binds to loopback by default. All POST routes run the browser-origin and Fetch Metadata guard, which permits requests with those headers absent. Timeline SSE has a similar guard. The machine and capability credentials below add narrower checks. See [server dispatch](hearth/server.py#L685), [POST guard](hearth/server.py#L865), and [deployment contract](docs/deploy.md#L3).

## Top five recommendations

1. **Verify and enforce the private Sprite boundary** (D01). Before the deadline, check the workspace edge setting and test reachability with a signed-out client against a disposable deployment. Confirm that the share service exposes only its intended snapshot interface.
2. **Keep untrusted content from authorizing tools** (D02, D11). Use synthetic web, browser, and email fixtures to check that content cannot grant permissions or change a destination. Prioritize effect and destination checks over expanding the phrase filter.
3. **Make background failure and restart recoverable** (D03–D05, D09–D10). Start with tests for a failed worker state write, overlapping tick paths, and restore during delivery. Add sanitized status for stuck or stale jobs. Preserve existing idempotency and commit guards.
4. **Bound foreground work with realistic histories** (D06, D12–D13). Measure state payloads, lock contention, and per-turn attachment work using generated fixtures. Prioritize a cheap, small snapshot and paged chat history before a database migration.
5. **Use regression tests to guide incremental extraction** (D07–D08, D14, D16–D17). Start with browser reconnect and final-reply accessibility tests plus tool-call behavior tests. Extract shared validation and reconciliation in small changes that preserve parent and worker behavior.

**Leave alone before November 29.** Defer a storage engine migration, scheduler rewrite, wholesale agent or web refactor, route renames, and compatibility cleanup. Preserve the existing approval defaults, worker limits, summary semantics, provider fallbacks, and Pages sandbox. Use the time for edge and wake verification and a fixture-based rehearsal of chat, approval, reminder delivery, and Page sharing. None of those operational checks were run against a live workspace for this review.
